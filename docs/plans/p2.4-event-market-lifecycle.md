# P2.4 — Event + Market Creation, Resolution, and Voiding

**GitHub issue:** [#34](https://github.com/Shisa-Fosho/services/issues/34)
**Branch:** `34-event-market-creation-resolution-voiding`

## Context

P2.3 (#33) shipped: `market_fee_rates` was folded into `markets.fee_rate_bps`, the `market-config` JetStream KV bucket exists, and `market.Publisher` already emits `PublishMarketConfig` (KV) and `PublishStatusChange` (Core NATS for WebSocket fan-out). The market admin surface today only handles category / event metadata, market metadata, pause/resume, and fee-rate changes — there is no creation, resolution, or void path, and no on-chain verification.

This issue plugs in the remaining lifecycle endpoints. Verification is done **directly** against the deployed `ConditionalTokens` contract via `ethclient` rather than waiting for an indexer event: the indexer (W2) owns deposits and settlement confirmations, not market lifecycle. The backend reads `getOutcomeSlotCount` / `payoutDenominator` / `payoutNumerators` at the moment the admin clicks "create" / "resolve" / "void" and only persists if the on-chain state matches.

It also adds three trading-config columns (`tick_size`, `min_size`, `max_size`) that the Polymarket clob-client v5.8.2 SDK exposes per market in `OrderBookSummary`. These were explicitly deferred from #33 to #34 and must land in the `market-config` KV payload so trading consumes them.

It also tightens the schema to match Polymarket's data model: every market belongs to an event and every event has at least one market. Confirmed against the [neg-risk-ctf-adapter docs](https://github.com/Polymarket/neg-risk-ctf-adapter/blob/main/docs/index.md): on-chain there is no "event" primitive — only conditions — and Polymarket's event-level grouping is the NegRiskAdapter `marketId` for multi-outcome events. Even single-outcome events (e.g. "BTC > $100k") are modelled as an event with one binary market. So this PR makes `markets.event_id` `NOT NULL` and removes the standalone-`CreateEvent` repository method; only `CreateEventWithMarkets` survives.

**On-chain identifiers — disambiguation.** Three on-chain identifiers can attach to a market, plus our DB primary key. They are NOT interchangeable, and naming-wise it's important to keep "marketId" (NegRiskAdapter concept) separate from "market ID" (our DB UUID):

| Field | Source | BINARY | NEG_RISK |
|---|---|---|---|
| `markets.id` | DB-generated UUID (our PK) | ✓ always | ✓ always |
| `markets.condition_id` | On-chain CT `conditionId` | ✓ admin-supplied | ✓ derived via `NegRiskAdapter.getConditionId` |
| `markets.question_id` | On-chain `questionId` | ✓ admin-supplied | ✓ admin-supplied (per market) |
| `events.neg_risk_market_id` | NegRiskAdapter `marketId` | ✗ never | ✓ admin-supplied (shared across markets in event) |

The DB UUID is what every other system in our stack (orders, positions, balances) refers to. The on-chain IDs only matter at the create / resolve / void boundary where we touch chain state. NegRisk markets carry **both** kinds of ID — a DB UUID (per market) AND the adapter `marketId` (on the parent event row).

**NegRisk creation + resolve in scope. NegRisk void deferred.** "Single-yes" events — mutually-exclusive multi-outcome events where at most one binary question can resolve YES (e.g. an N-candidate election) — are first-class for **creation** and **resolution**. They flow through the same `CreateEventWithMarkets` → resolve pipeline as binary events.

NegRisk voiding is **deferred entirely** because there is no clean on-chain primitive for it. `Helpers.payouts` in the adapter only emits `[1,0]` or `[0,1]` — never the `[1,1]` pattern that signals "void" on a binary CT market. Even with the optional `NegRiskOperator` contract, flag-and-never-resolve is a soft pause, not a true terminal void state. A NegRisk-specific void story is its own design problem and gets designed in a follow-up. This PR's `voidEvent` handler returns **400** for any event with `event_type=NEG_RISK`.

Two storage additions cover NegRisk: `events.neg_risk_market_id` (the adapter-level marketId, nullable, set only when `event_type = NEG_RISK`) and `markets.question_id` (the on-chain questionId, **NOT NULL — required for all markets**). The asymmetry is deliberate: every CT condition is derived from a questionId regardless of event type, but only NegRisk events have a top-level adapter marketId grouping multiple questions.

`question_id` is required for all markets because resolution is a two-phase flow from the admin's seat. **Phase one (chain):** the admin (acting as the oracle, since we have no automated oracle) calls `reportPayouts(questionId, [1,0])` for binary markets, or `NegRiskAdapter.reportOutcome(questionId, true)` for NegRisk — both require the questionId. Our DB is the source of truth the frontend reads to construct that transaction. **Phase two (backend):** the admin hits `POST /admin/events/{id}/resolve`; backend reads `payoutNumerators(conditionId)` to verify and persists state. Without question_id stored, phase one has no input.

On-chain verification for NegRisk uses the `ConditionalTokens` condition: the admin supplies `question_id` and the backend derives `condition_id` via `NegRiskAdapter.getConditionId` at create-time, persisting both. For BINARY the admin supplies both directly; we do NOT recompute conditionId from questionId (that would be a self-consistency check on three admin-supplied inputs, not a chain check — `getOutcomeSlotCount(conditionId)` against the actual chain is the authoritative verification). Resolve then reads `payoutNumerators` against `ConditionalTokens` exactly as in the binary path — `NegRiskAdapter.reportOutcome` internally calls `ctf.reportPayouts`, so the underlying CT state is the source of truth for resolution either way. A NegRisk-only **pre-check** also reads `NegRiskAdapter.getDetermined(marketId)` to reject a second YES with a clean 422 before the chain would revert.

Per-request order: **(1)** verify on-chain via `chainReader`, **(2)** commit to Postgres in one transaction (rolls back if anything fails), **(3)** publish to KV (`market-config`), **(4)** publish status change on Core NATS. ### 2. Chain readers — centralized under `internal/shared/eth/`

Per the centralized-reader convention in `.claude/rules/conventions.md` (On-chain Contract Bindings), each contract gets its own narrow reader interface in `internal/shared/eth/`, built on top of abigen-generated bindings. The platform service composes only the methods it needs.

**Files added:**

- `internal/shared/eth/abi/ConditionalTokens.json` and `NegRiskAdapter.json` — vendored from `shisa-contracts/abi/` (the canonical ABI exports). These are the only artifacts committed to the repo.
- `internal/shared/eth/generate.go` — `//go:generate abigen ...` directives, one per contract.
- `internal/shared/eth/gen/<contract>/` — **`.gitignore`d** abigen output. Regenerated by `make gen-contracts` (transitively by `make build` / `make test` / `make lint`).
- `internal/shared/eth/chain.go` — `Dial(ctx, rpcURL) → *ethclient.Client` factory + sentinel errors (`ErrConditionNotPrepared`, `ErrPayoutsNotReported`, `ErrNegRiskDisabled`).
- `internal/shared/eth/conditionaltokens.go` — narrow `CTReader` interface + concrete `*CTReaderClient` wrapping the abigen bindings:

  ```go
  type CTReader interface {
      OutcomeSlotCount(ctx context.Context, conditionID common.Hash) (uint64, error)
      PayoutDenominator(ctx context.Context, conditionID common.Hash) (*big.Int, error)
      PayoutNumerators(ctx context.Context, conditionID common.Hash, slotCount uint64) ([]*big.Int, error)
  }
  ```

- `internal/shared/eth/negrisk.go` — narrow `NegRiskReader` interface + concrete `*NegRiskReaderClient`:

  ```go
  type NegRiskReader interface {
      ConditionID(ctx context.Context, questionID common.Hash) (common.Hash, error)
      MarketDetermined(ctx context.Context, marketID common.Hash) (bool, error)
  }
  ```

  `NewNegRiskReader` accepts the zero address to mean "NegRisk not configured on this deploy"; the returned reader's methods all return `ErrNegRiskDisabled` in that case.

**NegRiskOperator is explicitly NOT modeled.** Its flag/delay primitives do not produce a terminal "voided" state, and NegRisk voiding is deferred entirely (see "Out of scope" below).

**Why centralized + abigen instead of hand-rolled ABIs:**

The same read methods will be reused across services as they land — settlement needs CT payouts + position math, indexer needs the same for event correlation, trading needs CTFExchange views. Putting per-contract readers in `internal/shared/eth/` avoids duplicated keccak math and ABI drift. Using abigen instead of hand-written ABI JSON literals catches typos at codegen time rather than runtime — the bug class that the unit-test-only validation pass would never have surfaced.

Extend `ValidateEvent` (or add a new `ValidateNegRiskCoherence(event, markets)` helper called from the repo) to enforce the NEG_RISK invariants at the domain layer:

- All event types: every market has `QuestionID != ""` and `ConditionID != ""` (no `nil`-checks because `QuestionID` is a non-pointer `string`; the empty-string check covers DB NOT NULL plus admin omissions caught at the request layer).
- `event_type == NEG_RISK` ⇒ `event.NegRiskMarketID != nil` AND the markets slice has length ≥ 2 (NegRisk by definition is mutually-exclusive multi-outcome — a single-market NegRisk event is meaningless).

**Note on `event_type` vs. multi-market grouping**: these are orthogonal. `event_type` describes on-chain settlement mechanics; multi-market grouping is a display concept. NegRisk's multi-market shape carries the *additional* on-chain semantic that at most one question resolves YES across the group, enforced by the adapter. Don't confuse the two axes.

```go
// CreateEventWithMarkets inserts an event and its markets in one transaction. Returns ErrDuplicateSlug on either
// side (event slug, market slug, condition ID, or question ID), ErrInvalidEvent / ErrInvalidMarket on shape
// violations, and ErrInvalidEvent if markets is empty (every event must have at least one market). All markets
// get status = Active.
CreateEventWithMarkets(ctx context.Context, event *Event, markets []*Market) (*Event, []*Market, error)

// ResolveMarketsInEvent atomically transitions the markets named in `outcomes` to Resolved with the supplied
// outcome. Other markets in the event are left untouched. If, after the update, every market in the event is
// in a terminal status (Resolved or Voided), event.status is auto-flipped to Resolved. Returns ErrNotFound for
// missing event, ErrInvalidMarket if any key in `outcomes` doesn't belong to this event, ErrInvalidTransition
// if any named market is not currently Active, and ErrInvalidEvent if outcomes is empty.
ResolveMarketsInEvent(ctx context.Context, eventID string, outcomes map[string]Outcome) (*Event, []*Market, error)

// VoidMarketsInEvent is the void-path counterpart for BINARY events. Caller supplies the IDs of markets to
// void; others stay untouched. Same auto-flip rule: event.status becomes Voided only if every market is voided;
// if a mix of Resolved + Voided covers all markets, event.status becomes Resolved. Same error contract.
//
// Note: the handler rejects this path for NEG_RISK events at the HTTP layer (400). The repo doesn't enforce
// that; callers in tests can exercise the path with synthetic NEG_RISK rows if needed.
VoidMarketsInEvent(ctx context.Context, eventID string, marketIDs []string) (*Event, []*Market, error)

// UpdateTradingConfig writes tick_size/min_size/max_size onto a market and returns the resulting row. Returns
// ErrInvalidMarket for shape violations and ErrNotFound if the market does not exist.
UpdateTradingConfig(ctx context.Context, marketID string, tickSize TickSize, minSize int64, maxSize *int64) (*Market, error)
```

Implementation notes for `pg_repository.go`:

- `CreateEventWithMarkets` uses `pool.Begin → defer Rollback → tx.Commit`, inserting the event with `RETURNING id, created_at, updated_at`, then looping over markets (insert with FK = event id and `RETURNING *`). Reuses `ValidateEvent` and `ValidateMarket`, mapping `postgres.IsUniqueViolation` to `ErrDuplicateSlug`. Empty markets slice → `ErrInvalidEvent`.
- `ResolveMarketsInEvent` and `VoidMarketsInEvent` share a transactional helper:
  1. `BEGIN`, `SELECT id FROM events WHERE id=$1 FOR UPDATE` (404 if missing).
  2. `SELECT id, status FROM markets WHERE event_id=$1 FOR UPDATE` — pulls every sibling for the auto-flip decision and locks them.
  3. Validate the supplied keys are all members and currently `Active` (`ValidateStatusTransition`).
  4. `UPDATE markets SET status='RESOLVED', outcome=$N, updated_at=now() WHERE id = ANY($X) RETURNING *` (or `status='VOIDED'`, no outcome).
  5. Compute `allTerminal := every sibling.status ∈ {Resolved, Voided}` after the update. If yes, update the event row; otherwise leave event.status as-is. The event row is returned in either case.
  6. `COMMIT`.
- `UpdateTradingConfig` follows the same shape as `UpdateFeeRate`.

#### `POST /admin/events`

Request body shape, BINARY:

```json
{
  "slug": "...", "title": "...", "description": "...",
  "category_id": "...", "event_type": "BINARY", "end_date": "RFC3339",
  "markets": [{
    "slug": "...", "question": "...",
    "outcome_yes_label": "Yes", "outcome_no_label": "No",
    "token_id_yes": "0x...", "token_id_no": "0x...",
    "condition_id": "0x...", "question_id": "0x...",
    "tick_size": "0.01", "min_size": 5, "max_size": null
  }]
}
```

Request body shape, NEG_RISK (note: `condition_id` is omitted — the backend derives it from `question_id` via `NegRiskAdapter.getConditionId`):

```json
{
  "slug": "...", "title": "...", "description": "...",
  "category_id": "...", "event_type": "NEG_RISK", "end_date": "RFC3339",
  "neg_risk_market_id": "0x...",
  "markets": [
    {
      "slug": "alice", "question": "Will Alice win?",
      "outcome_yes_label": "Yes", "outcome_no_label": "No",
      "token_id_yes": "0x...", "token_id_no": "0x...",
      "question_id": "0x...",
      "tick_size": "0.01", "min_size": 5, "max_size": null
    },
    { "slug": "bob", "...": "..." }
  ]
}
```

Flow:

1. Decode + basic shape validation. Reject 400 on missing `markets`, missing `tick_size`/`min_size`, missing `question_id` on any market, or shape mismatches against `event_type`:
   - BINARY: ≥ 1 market, each with both `condition_id` AND `question_id` supplied. No `neg_risk_market_id` on the event.
   - NEG_RISK: ≥ 2 markets, each with `question_id` supplied (no `condition_id` — the backend derives it). Event-level `neg_risk_market_id` is required.

   `question_id` is required for ALL markets across both event types. Build domain `Event` and `[]*Market` in memory.
2. **Resolve every market's `condition_id`:**
   - BINARY: use the supplied `condition_id` as-is. `ConditionalTokens` does expose `getConditionId(oracle, questionId, outcomeSlotCount)` which is just `keccak256(abi.encodePacked(...))` — we deliberately do NOT recompute and compare. It's pure derivation from three admin-supplied inputs (no chain state involved), so a passing recompute proves nothing the chain doesn't already prove. The authoritative check is `OutcomeSlotCount(conditionId) == 2` in step 3, which reads actual chain state. Skipping the recompute also means we don't have to ask the admin for `oracle` on every request.
   - NEG_RISK: for each market, call `chainReader.NegRiskConditionID(ctx, questionID)` to derive the conditionId from the adapter and write it into the in-memory `Market.ConditionID`. Unlike CT's pure derivation, the adapter applies its own salts/encoding the admin can't easily replicate off-chain, so we own the derivation. RPC failure → 502.
3. For each market: call `chainReader.OutcomeSlotCount(ctx, conditionID)`.
   - 0 → `ErrConditionNotPrepared` → 422 "condition not prepared on-chain" (NEG_RISK case: this means the question wasn't actually prepared on the adapter — the derived conditionId is deterministic from inputs and exists in the namespace whether or not anyone called `prepareQuestion`, so the slot-count read is the real preparedness check).
   - != 2 → 422 "outcome slot count mismatch".
4. Call `repo.CreateEventWithMarkets`. Map errors:
   - `ErrDuplicateSlug` (event slug, market slug, condition_id, or question_id — both `markets_condition_id_unique` and `markets_question_id_unique` trip the same path) → 409.
   - `ErrInvalidEvent` / `ErrInvalidMarket` → 400.
5. For every market, `publisher.PublishMarketConfig(market)`. If any fails → 502 with `publishFailed`.
6. Return 201 with the event body + nested markets (including the server-derived `condition_id` for NEG_RISK markets, so the admin can audit it).

#### `POST /admin/events/{id}/resolve`

Request body — partial resolution is supported; `outcomes` may name a **subset** of the event's markets:

```json
{
  "tx_hash": "0x...",
  "outcomes": { "<market_id>": "YES" | "NO" }
}
```

Flow:

1. Load event + its markets (read-only) so we can verify on-chain state for each market named in `outcomes`. 404 if event missing.
The flow is "admin already resolved on-chain; backend verifies their declared outcomes match the chain state before mirroring it into our DB". Concretely:

2. For each market in `outcomes`:
   - Verify the market belongs to this event. 422 if not.
   - `denom := chainReader.PayoutDenominator(ctx, conditionID)`. If `denom == 0` → 422 "payouts not reported on-chain" (admin called our API before completing the chain step for this question).
   - `nums := chainReader.PayoutNumerators(ctx, conditionID, 2)` — by CT convention, index 0 = YES, index 1 = NO.
   - Cross-check the admin's declared outcome against chain state:
     - Admin said YES → require `nums[0] > 0 && nums[1] == 0`.
     - Admin said NO  → require `nums[0] == 0 && nums[1] > 0`.
     - Anything else → 422 with `ErrOnChainMismatch` (admin lied or typo'd; chain wins).

This per-market chain check is the primary verification and is sufficient on its own. The reason: if the admin claims `{m_x: "YES"}` for a NegRisk question that isn't actually the YES, then `q_x`'s `payoutNumerators` will be `[0,0]` (the adapter never called `reportPayouts` for q_x because no `reportOutcome(q_x, true)` ever ran), so `denom == 0` → clean 422 from the per-market check above.

**Optional NegRisk-specific friendlier error**: when the per-market check 422s with `denom == 0` AND `event_type == NEG_RISK` AND `chainReader.NegRiskMarketDetermined(ctx, event.NegRiskMarketID) == true`, swap the error message from "payouts not reported on-chain" to "another market in this NegRisk event already resolved YES; this question can never be reported". Same 422 code, different message — better UX when the admin tries to declare a second YES. The `NegRiskMarketDetermined` read is only done in this branch, so it's cheap. Worth doing if it's a one-liner; safe to drop if it adds noise.

For a 3-market NegRisk event where on-chain state is q1=YES, q2=NO, q3=NO and the admin POSTs `{m1: "YES", m2: "NO", m3: "NO"}`: per-market checks pass for all three (m1's nums=[1,0] matches YES; m2 and m3 have nums=[0,1] from `reportOutcome(q, false)` matching NO). Repo writes all three rows + auto-flips event.status to Resolved.
3. `repo.ResolveMarketsInEvent(ctx, eventID, outcomes)` — atomic; only the markets in `outcomes` flip; siblings stay Active. Event row auto-flips to Resolved iff every sibling is now terminal (see repo notes).
4. For each market that actually transitioned: KV `PublishMarketConfig`, then Core NATS `PublishStatusChangeWithOutcome` carrying the outcome. Either failure → 502 (`publishFailed`).
5. Return 200 with the updated event + markets (the response includes sibling markets in their unchanged state so callers see the full event).

Notes: the on-chain `tx_hash` is recorded for audit but does not gate verification — the `payoutDenominator` / `payoutNumerators` reads are state-based and idempotent. Partial resolution mirrors the on-chain reality: in NegRisk events each binary question resolves on its own schedule via per-question `NegRiskAdapter.reportOutcome`, which internally invokes `ctf.reportPayouts` against the underlying condition. Because the verification path reads `payoutNumerators` against `ConditionalTokens` keyed off the stored `condition_id`, this endpoint works for BINARY and NEG_RISK alike. The only NegRisk-specific branching is the pre-check above.

#### `POST /admin/events/{id}/void`

**NegRisk events return 400 unconditionally — voiding NegRisk is deferred (see "Out of scope" below).**

```json
{"error": "void_not_supported_for_negrisk", "message": "voiding NegRisk markets is not yet supported"}
```

For BINARY events, request body supports the partial-subset shape:

```json
{ "tx_hash": "0x...", "market_ids": ["..."] }
```

If `market_ids` is omitted, default to "every market currently in Active status for this event" (admin convenience for the common "void everything" case). On-chain check per market: all `payoutNumerators[i]` equal AND `> 0` (e.g. `[1,1]`). Anything else → 422. Repo call: `repo.VoidMarketsInEvent(ctx, eventID, ids)`. Publishes same as resolve but with `outcome = nil`.

#### `PUT /admin/markets/{id}/trading-config`

Request body:

```json
{ "tick_size": "0.01", "min_size": 5, "max_size": 1000 }
```

Flow: validate via `ValidateTradingConfigUpdate`, call `repo.UpdateTradingConfig`, then `publisher.PublishMarketConfig` — **fatal on publish failure** per AC. No status-change broadcast (status is unchanged).

## Out of scope (explicit)

- **NegRisk market voiding.** Deferred entirely. There is no on-chain primitive that produces a clean terminal "voided" state for a NegRisk question — `Helpers.payouts` only emits `[1,0]` or `[0,1]`, never `[1,1]`. The optional `NegRiskOperator` contract adds flag-and-delay primitives but still resolves to YES or NO in the end. The handler rejects 400 for `event_type=NEG_RISK` on the void endpoint. A follow-up issue will design what "void" means in the NegRisk UX (e.g. Operator deployment + a documented refund convention) and unblock this path.
- **Frontend follow-up:** the admin UI must hide the "void" button for events where `event_type=NEG_RISK`. Lives in a separate repo — flagged in the PR description so the frontend issue gets created.
- Trading-side reaction to `RESOLVED` / `VOIDED` (cancelling open orders) — that's a trading-service follow-up; this issue only publishes the state.
- **NegRisk capital-efficient conversion.** The adapter's `convertPositions` flow (burning a full set of NO positions across every question to mint a single YES + collateral) and the `_results` bitmap that gates it are *trading-side* mechanics. This PR creates and resolves NegRisk events but does not expose conversion to traders; that lands with the NegRiskCtfExchange.
- Position-ID derivation (`getCollectionId` + ERC-1155 `getPositionId`) for token-ID cross-checking. We verify slot count == 2; strict position-ID derivation is a follow-up if mismatch incidents appear.
- Deploying `CTFExchange`, `NegRiskCtfExchange`, `UmaCtfAdapter` to the Anvil container. The seed script in this PR deploys `ConditionalTokens` + `NegRiskAdapter` + mock ERC-20 collateral, which is sufficient for the lifecycle endpoints (binary + NegRisk create/resolve). The exchange contracts land alongside the consuming trading features; `UmaCtfAdapter` lands with UMA-driven settlement.
